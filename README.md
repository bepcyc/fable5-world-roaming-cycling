# LAAS

*laas — Estonian for old-growth forest.*

![Procedural open world rendered in the browser](docs/readme-hero.jpg)

Unedited engine output. Every mesh, texture, and light in this frame is generated by code at boot — apart from the CC0 rider model and the app icon/splash imagery, the repository carries no art assets.

LAAS is two things in one repository:

- **The world** — a fully procedural 4×4 km open world running in the browser on WebGPU: three.js `WebGPURenderer` with TSL materials and raw WGSL compute, TypeScript strict with zero `any`, no WebGL fallback. The entire world is reproducible from a single URL parameter (`?seed=N`).
- **The ride** — *Project Rando*, a first-person hike & bike sim built on that world: three bikes on a generated road network, driven by real BLE trainer/sensor data (Zwift-class), with ride recording and Strava upload. Brief: [docs/PROJECT_RIDE_v1.md](docs/PROJECT_RIDE_v1.md).

## The experiment

The goal of this project is to test the capabilities of Claude Fable 5, Anthropic's newest model. This repository was built roughly 99% by the model, with minimal human steering:

- The human partially wrote one document: [PROJECT_LAAS_v2.md](PROJECT_LAAS_v2.md) — the brief. It sets the visual bar (UE5-class reference frames), hard floors (triangle counts, system list, world size), and banned outcomes (black shadows, cloned trees, fog as cover). It deliberately does not say how to build any of it. The ride layer's own brief, [docs/PROJECT_RIDE_v1.md](docs/PROJECT_RIDE_v1.md), followed the same pattern.
- Everything else was planned and executed by Fable 5 across long autonomous sessions: the architecture, all engine and world systems, the ride layer, the verification tooling, the debugging, the working notes, and this README.
- Human input is limited to rare feedback on the things a model cannot judge well from static output: whether motion effects feel right, whether interactive performance holds up, whether an artifact is visible while moving. Examples from the log: wind sway amplitude, walk-camera bob, cloud motion lagging the camera, water coverage taste.

The model does its own QA. It boots the world headless (Playwright driving Chromium with a WebGPU/Metal adapter), takes screenshots, samples pixels, diffs frames against baselines with frame-aligned determinism, profiles GPU passes per encoder, and writes regression probes for the bugs it finds. The diagnosis logs, measurements, and decisions live in [STATUS.md](docs/log/STATUS.md), which serves as the model's durable memory between sessions.

Current state (v0.8.0): about 52,000 lines of strict TypeScript across 164 files and 300+ commits — engine, world, and the ride layer — with an ongoing performance pass. Known open issues are tracked at the top of docs/log/STATUS.md.

## What is in the world

- Terrain: 4096² heightfield synthesis, pipe-model hydraulic plus thermal erosion, flow-accumulation rivers carving real channels into lakes with outlets, moisture and biome classification, slope- and exposure-driven snow. CDLOD quadtree meshing with crack-free skirts and far-shell detail synthesis to a 4 km+ visible range.
- Vegetation: six tree species grown by a procedural branching grammar with per-instance uniqueness (no two trees share a mesh), cluster-card foliage baked from real generated leaf geometry, octahedral impostors, three shrub classes, ferns, flowering plants, deadfall with decay states. Around 190,000 trees and 450,000 understory instances are placed by GPU clustered-Poisson scatter and culled per frame into compacted indirect draws; meadows render roughly a million grass blades.
- Lighting: four-cascade shadow maps with PCSS and screen-space contact shadows, a terrain-relative irradiance-probe field for GI, GTAO, screen-space bounce, foliage translucency. A no-black-shadows rule is enforced by automated pixel sampling.
- Atmosphere: Hillaire LUT atmosphere driving sky, aerial perspective and light color; raymarched volumetric clouds with cloud shadows; froxel volumetrics for canopy light shafts and valley fog.
- Water: stream and lake surfaces on a camera-following clipmap, screen-space reflections with terrain-aware fallbacks, analytic caustics, obstacle foam, wet margins.
- Motion: hierarchical wind through every plant, 131,072 GPU particles (snow, pollen, drifting leaves), drifting and churning cloud fields.
- Post: temporal AA with analytic camera-reprojection velocity, bloom, GPU auto-exposure, per-time-of-day filmic grade.
- Exploration: walk mode with gravity, jumping, sprint and stride-matched camera motion; free-fly mode; nine composed bookmarks; a 90-second flythrough.

## What is in the ride

- Routes: a generated road & trail network (`src/ride/RoadNetwork.ts`, `RouteGraph.ts`) with junctions and tagged surfaces — asphalt, fine/coarse gravel, dirt, singletrack — plus off-network terrain classes. Arrow keys pick a turn before each junction.
- Bikes: road, gravel, MTB (`src/ride/BikeRig.ts`), each governed by a single surface×mode matrix (`src/ride/SurfaceMatrix.ts`) — rolling resistance, grip, max speed, stall risk per surface. Road bikes fade off pavement; the MTB goes almost anywhere.
- Physics: a natural power solver `P = (Crr·m·g·cosθ + m·g·sinθ + ½ρ·Cd·A·v²)·v` (`src/ride/BikeSolver.ts`) — real 9.81 m/s² gravity, gradient read from the actual heightfield, no arcade tuning.
- Sensors (`src/ride/ble/`): real BLE data drives the bike — FTMS trainers incl. control point, Tacx FE-C, cycling power, speed/cadence (CSC), heart rate (HRS), running speed/cadence (RSC), plus vendor machines (Concept2, KayakFirst, LifeFitness, Precor, Schwinn X70). Three transports behind one seam: Web Bluetooth on desktop, a native Kotlin bridge in the Android APK, and a scripted fake for probes.
- Cockpit: first-person handlebars, hands, and a per-bike-class cycling computer (`src/ride/cockpit/`).
- HUD: toggleable Zwift-style dashboard cards — speed, cadence, heart rate, power (`src/ride/RideHud.ts`).
- Recording: pause/finish menu (P) with save-as-`.fit`/`.tcx`/`.csv`/`.json` or sync-to-Strava via OAuth upload (`src/ride/session/`, `src/ride/strava/`); FIT/CSV replay import feeds the probe harness (`src/ride/replay/`).
- Ride entry: `?ride=ble` real sensors · `?ride=demo` synthetic source (always DEMO-badged, never writes ride stats) · `?ride=blefake` scripted fake for probes · `?ridedev=1` keyboard bike (dev). Add `?road=<class>` to spawn on a road.

## Surfaces

- **Web** — `npm run dev` → http://localhost:5173; the production build serves under a `/laas/` base path.
- **Desktop** — `just linux-binary` → Electron AppImage (bundled Chromium, loopback origin so WebGPU + Web Bluetooth work).
- **Android** — `just android-apk` → debug APK that bundles `dist/`, serves it from a 127.0.0.1 loopback inside a Chrome Custom Tab, and bridges BLE natively. See [docs/PACKAGING.md](docs/PACKAGING.md) for why everything ships a Chromium.

## Running it

```
npm install
npm run dev
```

Open `http://localhost:5173` in Google Chrome 113 or newer on a desktop or laptop. Other Chromium-based browsers (Edge, Brave, Arc, Opera) should work too. Safari and Firefox are not supported — the engine is built and tested against Chrome's WebGPU implementation, and the page detects this before loading and says so. Mobile and tablet browsers get a notice recommending a computer. There is no WebGL fallback by design: if Chrome is present but WebGPU is unavailable, the page fails loudly with diagnostics and the exact things to check (hardware acceleration, `chrome://gpu`, browser version).

Controls (hike): click to capture the mouse. WASD to move, Shift to sprint, Space to jump, V toggles walk/fly, mouse wheel sets fly speed, E/Q move vertically in fly mode. Keys 1–9 jump to composed bookmarks, F starts the flythrough, F3 opens the debug HUD with per-pass GPU timings, P prints the current camera pose as a `?cam=` string.

Controls (ride, `?ridedev=1`): W/↑ pedal, Shift sprint, Space/S/↓ brake, ←/→ pick a junction turn, M cycle bike (road/gravel/MTB), X dismount, B toggle the dashboard, P ride menu, Ctrl+E download a draft `.fit`.

Useful URL parameters: `?seed=N` (world seed), `?T=hours` (time of day, 0–24), `?shot=1..9` (boot into a bookmark), `?cam=x,y,z,yaw,pitch[,fov]` (exact pose), `?preset=low|high|ultra`, `?freeze=1` (freeze world motion), `?hud=1` (HUD open at boot), `?debug=1` (boot diagnostic overlay + telemetry sink).

Contributing: prerequisites, the full command map, and what runs in CI vs. on GPU hardware live in [CONTRIBUTING.md](CONTRIBUTING.md).

## Verifying

`npm run typecheck` (strict tsc) · `npm test` (vitest, pure-logic suites) · `npm run build` — these three run in CI on every push. The visual/physics gates (`npm run gates:*`) and the ~80 `tools/probe-*.ts` scripts need a WebGPU-capable GPU with Chromium and run on the owner's hardware only.

## Troubleshooting

- **Boot gate refuses to load** — use Chrome 113+; check `chrome://gpu` shows WebGPU "Hardware accelerated" and that hardware acceleration is on. The gate page lists the exact failing check.
- **`?debug=1`** — on-screen boot overlay (adapter identity, limits, timed steps) plus a reverse telemetry channel; see [docs/LAUNCH_AND_DEBUG.md](docs/LAUNCH_AND_DEBUG.md).
- **`?log=debug|info|warn|error|silent`** — console verbosity; default `warn` keeps a boot quiet. `?log=debug` restores the adapter diag + build chatter (`[tag]`-prefixed lines).
- **GPU process crashes when riding (headed Chrome only)** — never pass `--use-angle=vulkan`; Dawn's own Vulkan backend must not share the GPU with ANGLE's GL-on-Vulkan client. Details in `tools/probe-real-crash.ts`.
- **Phone/tablet can't reach the dev server** — WebGPU + Web Bluetooth need a secure context: whitelist `http://<IP>:5173` once in `chrome://flags/#unsafely-treat-insecure-origin-as-secure`, then open `http://<IP>:5173/?nogate=1` (`just run-lan` prints this).
- **Slow on a weaker GPU** — `?preset=low&dpr=1` is the mobile floor profile; F3 shows per-pass GPU timings.
